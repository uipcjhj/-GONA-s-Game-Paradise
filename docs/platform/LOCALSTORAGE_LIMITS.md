# 데이터 안정성 · localStorage 의 한계

## 1. 단일 상태 + 원자적 갱신 (코인·XP·업적·구매가 어긋나지 않는 이유)
- 게임천국의 모든 상태(기록·XP·코인·레벨·업적·칭호·도감·미션·출석·상점/장착·구매 내역·중복 방지 원장)는 **`PlayerData` 객체 하나**(`gp.v1.player`)에 있다.
- 모든 규칙은 **순수 함수**(`src/platform/engine.ts`): `(이전 데이터, 입력) → (새 데이터, 알림)`. 보상 지급·업적 해금·레벨업·도감 발견·칭호 해금이 **한 번의 계산 안에서** 끝난 뒤 **한 번만 저장**한다. 중간 상태가 저장되지 않으므로 "코인은 늘었는데 업적은 없음" 같은 불일치가 생기지 않는다.
- 불변식(테스트로 검증): `coinBalance = totalCoinsEarned − Σ(구매 가격)`, `totalXP = totalXpEarned`, `coinBalance ≥ 0`, `레벨 = levelForXp(totalXP)`, 레벨 보상은 레벨당 1회, 업적·도감·미션 보상은 1회.
- 변경 직전에 **저장소에서 최신본을 다시 읽어** 적용한다(다른 탭이 먼저 바꿨어도 덮어쓰지 않음). 저장 시 직전 정상본을 `.bak` 로 남긴다.
- 게임 결과 수신은 2단계: ① inbox 읽기·검증·메모리 반영 ② **플레이어 저장 성공 후에만** inbox 삭제. 저장은 성공했는데 삭제 전에 꺼져도 다음 실행에서 `resultLedger`(resultId) 로 건너뛴다. 저장 실패 시 inbox 를 남겨 재시도한다.

## 2. 검증한 상황 (단위 · 브라우저 테스트)
새로고침 · 강제 종료(저장 후 삭제 전 크래시 시뮬레이션) · 중복 이벤트/동일 세션·결과 재전송 · 두 탭 동시 수신(Web Locks + 원장) · 백업 복원(v1/v2) · 초기화(gp.v1.* 만 삭제) · v1→v2 마이그레이션 · 잘못된 결과(형식/범위/시간/세션/플레이어/크기/버전) · 저장 공간 부족(QuotaExceeded → 저장 실패 화면 + 재시도) · localStorage 접근 차단(메모리 모드 + 안내) · 비정상 날짜(시계를 과거로: 출석/미션 중복 지급 없음).

## 3. 한계 — 정직한 표기
- **로컬 기록은 조작할 수 있다.** localStorage 는 같은 출처의 모든 페이지·사용자가 읽고 쓸 수 있고, 개발자 도구로 값을 바꿀 수 있다. 게임이 보내는 결과도 마찬가지다. 따라서 코인·XP·업적·기록은 **온라인 인증/검증된 값이 아니다.**
- **구현된 방어는 "실수·단순 조작 걸러내기" 수준**이다: 형식·범위·시간·세션·플레이어 일치 검증, 점수 한도(시간 기반), 하루/세션 보상 한도, 중복 원장. 결심한 조작자는 막지 못한다. 온라인 랭킹에는 로컬 점수를 검증된 점수로 쓰지 않는다(서버가 세션 시간을 직접 재는 별도 경로 — `backend/API_CONTRACT.md`, 아직 미연결).
- **날짜는 기기 시계(한국 시간 환산) 기준**이다. 시계를 미래로 돌려 출석/미션을 앞당길 수는 있다. 되돌리기에 의한 중복 지급만 막는다(지금까지 본 가장 늦은 날짜를 '오늘'로 사용). 그래서 출석·미션 보상은 소액·무가치 재화(게임 코인)로만 설계했다.
- **브라우저 저장소 삭제·기기 변경·Safari 의 7일 미사용 정리** 등으로 기록이 사라질 수 있다 → 설정의 **파일 백업**을 권장하고 등록/설정 화면에 안내한다. 서버 복구 코드는 백엔드 구축 단계(D8)에서 결정.
- **용량**: localStorage 는 보통 ~5MB. 플레이어 데이터는 수 KB 수준이며(최근 기록 20개·원장 100개·구매 내역 100개로 상한) 가득 차면 저장 실패 화면으로 안내한다.
- **개인정보**: 닉네임·식별코드·기록만 이 기기에 저장. 이메일·비밀번호·소셜 로그인 없음.
- 같은 출처(`uipcjhj.github.io`)의 Food Adventure 와 키 공간을 분리(`gp.v1.*` vs `dino-snack-adventure.*`/`gona.*`)하지만, 이는 **보안 경계가 아니라 이름 충돌 방지**다.
